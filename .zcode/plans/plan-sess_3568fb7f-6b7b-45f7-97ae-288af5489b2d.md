Carte « Machine courante » dans le wizard Remote Connect (web) — l'agent atteint l'hôte du conteneur par la porte SSH

## Conception validée (tes 3 réponses)

**Principe** : c'est la doctrine du projet appliquée à l'hôte lui-même — le conteneur reste un bac à sable **intègre** (aucune capability, pas de socket Docker, pas de `pid:host`) et l'agent atteint la machine par **la porte SSH**, avec les credentials de l'opérateur, chiffrées et révocables. Sous le capot, c'est strictement le flux Remote SSH existant : deploy versionné du runtime sur l'hôte (`~/.zcode`, coexiste avec tes runtimes desktop), sessions durables PR #30 (la session hôte **survit au refresh** — gros bonus gratuit), historique et reconnexion inclus.

**Décisions** : auth par password stocké chiffré (flux existant) · carte visible **par défaut** en web, désactivable par env (`ZCLOUDIUM_HOST_MACHINE=off` — opinionated mais pas forcé) · formulaire auto-détecté et pré-rempli, champs éditables.

## Implémentation (patch series, 6e commit — ~7 fichiers)

1. **Détection** — `GET /api/host-machine` (session gateway requise) : `host` = gateway IP du bridge Docker lue dans `/proc/net/route` (depuis le conteneur, c'est l'hôte) avec override env `ZCLOUDIUM_HOST_SSH_HOST` ; `port: 22` ; `username` = env optionnelle, sinon vide. Route enregistrée seulement si la feature est active.
2. **Env + capability** — `ZCLOUDIUM_HOST_MACHINE` (défaut on, mêmes valeurs off que ZCLOUDIUM_AUTH) ; `createServerInfo` gagne `capabilities.hostMachine` ; `main.tsx` (qui fetch déjà server-info au boot) pose `platform.supportsHostMachineConnect = true` sur le platform web. Desktop ne le pose jamais → carte invisible là-bas.
3. **Wizard** — `buildAvailableKinds` pousse `"host"` si la capability ; carte avec icône dédiée + i18n (en-US/zh-CN : « Machine courante » / « Current machine (host) ») ; test-id `TID_REMOTE_KIND_HOST`. Le settings step de "host" = le formulaire SSH existant pré-rempli (fetch `/api/host-machine` à l'entrée du step, une fois, champs éditables) ; `buildRemoteTarget` pour "host" génère un **target SSH normal** — le serveur ne voit aucune différence : deploy, sessions durables, historique, attachments, MCP : tout le downstream marche gratuitement.
4. **Durcissement inchangé** — umask 077, credentials AES-GCM 0600 dans le volume, conteneur read-only non-root.

## Pré-flight et vigilance (premiers pas d'implémentation)

- Vérifier sur la prod que `PasswordAuthentication yes` sur le sshd de l'hôte (je ne pouvais pas le lire en plan mode). Si non : la clé privée posée dans `/data` + `privateKeyPath=/data/...` fonctionne déjà via le wizard — documenté en fallback.
- Host key checking du backend ssh2 au premier connect : à vérifier/fixer (accept + log de la fingerprint, pattern standard).
- Le deploy du runtime (~80 Mo, depuis le cache volume) s'installe dans `~/.zcode` de l'hôte — **additif et versionné**, coexiste avec tes runtimes desktop, nulle part on ne supprime rien.

## Complexité et scope

**Pas out of scope du tout** — c'est le produit full-web qui atteint son propre hôte par la porte standard. Effort : faible-modéré (~250 lignes, 7 fichiers, tout le plumbing existe). Le seul débat philosophique (conteneur qui touche son hôte) est tranché par la doctrine : par SSH, avec credentials, révocable — jamais en élargissant le conteneur.
